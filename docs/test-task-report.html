Лендинг: https://pet-landing.vercel.app/

Завдання 1 — що зроблено

  • Лендинг у ніші casino-агрегатора: hero з оффером, ранжування казино, інтерактивний підбір, відгуки, FAQ — шлях paid traffic → landing → lead. Mobile-first, перевірено на 390 / 768 / 1280 px.
  • Лід-форма (ім'я + email) з прихованими полями атрибуції; подія Lead генерується строго при відправці форми.
  • Thank-you стан: конверсійна подія спрацьовує один раз у момент переходу до стану подяки, не повторюється при оновленні сторінки.
  • React (бонусний пункт), маршрути /terms і /privacy, code splitting, self-hosted шрифти, security-заголовки (CSP без unsafe-inline у script-src, HSTS, X-Frame-Options/frame-ancestors), robots.txt, sitemap.xml.
  • GDPR: cookie-consent банер з Google Consent Mode v2 — жоден трекер не завантажується до згоди.
  • Якість: 27 юніт-тестів (Vitest) на логіку атрибуції, consent-гейтинг і події; лінт + типізація без помилок.
Важливо для перевірки трекінгу: на сайті є cookie-банер. Перед тестуванням подій натисніть Accept — до згоди Meta Pixel / GTM / GA4 навмисно не завантажуються (вимога GDPR/ePrivacy, реалізовано через Google Consent Mode v2: default denied → update granted).

Схема гібридна: прямі виклики gtag/fbq працюють «з коробки», а паралельні dataLayer-події (page_view, generate_lead з повним набором атрибуційних параметрів) дозволяють вести ті самі конверсії через теги GTM-контейнера. У контейнері при цьому не повинно бути дубльованих тегів GA4/Pixel на ці самі події (інакше конверсії задвояться) — контейнер використовується для розширень, прямі виклики є первинним каналом.

UTM та Click ID

Перелік параметрів, що відстежуються: utm_source, utm_medium, utm_campaign, utm_term, utm_content, clickid, subid, fbclid, gclid, gbraid, wbraid, ttclid, msclkid.

  1. Зчитуються з query string при першому візиті (first-touch: зберігаються також landing_url і first_touch_at; повторний візит з новими мітками оновлює їх, не втрачаючи дату першого дотику).
  2. Зберігаються в localStorage (ключ sl_tracking) — переживають навігацію по сайту.
  3. Передаються: у приховані поля лід-форми, у кожну dataLayer-подію, у параметри GA4-подій, і логуються в консоль (префікс [tracking]).

Перевірити можна, відкривши сайт з міткою, напр.: https://pet-landing.vercel.app/?utm_source=facebook&utm_campaign=test&fbclid=TEST123 — після Accept у консолі буде [tracking] init із захопленими параметрами, а в формі — приховані поля з цими значеннями.

Завдання 2 — де губиться Click ID у зв'язці Meta → Keitaro → Landing → Platform → Postback

Симптом: кліки в Keitaro фіксуються, postback приходить з HTTP 200, але subid порожній → конверсії не прив'язуються. HTTP 200 нічого не гарантує: Keitaro відповідає 200 навіть на postback без валідного subid.

1. Усі можливі точки втрати

  1. Оголошення веде повз Keitaro. У Meta в якості фінального URL стоїть прямий лінк на лендинг, а не кампанійний лінк Keitaro → клік не реєструється, subid взагалі не генерується (але тоді б і кліки не фіксувались — за умовою фіксуються, отже точка нижче).
  2. Tracking URL Keitaro → лендинг: макрос не підставляється. У шаблоні https://site.com/?clickid={subid}&fbclid={fbclid} помилка синтаксису макроса (не той регістр/назва, фігурні дужки одинарні замість потрібного формату) → на лендинг приходить clickid={subid} літералом або порожнім.
  3. Редиректи до лендингу зрізають query string. http→https, non-www→www, trailing slash редирект на хостингу/CDN, який не зберігає параметри → лендинг відкривається вже без clickid.
  4. Лендинг не зберігає clickid. Скрипт не зчитує параметр, зчитує під іншою назвою (чекає subid, а приходить clickid), губить його при внутрішній навігації (SPA/редирект на сторінку оффера без параметрів), або зберігає лише в cookie, яку блокує ITP/consent.
  5. Вихідний лінк лендинг → платформа не несе subid. Кнопка CTA — захардкоджений афілейт-лінк без підстановки; або subid кладеться не в той параметр, який платформа вважає своїм sub-параметром (subid vs aff_sub vs s1 vs var1); або редирект-ланцюжок платформи (лендинг → трекер оффера → казино) губить параметр на одному з хопів.
  6. Платформа не прив'язує subid до гравця. Значення дійшло до кліка, але платформа зберігає sub-параметри лише з першого кліка/сесії, а реєстрація сталась в іншій сесії (інший пристрій, in-app браузер Meta → системний браузер) → у профілі гравця sub порожній.
  7. Шаблон postback на боці платформи. У URL postback вписано ${subid}, але платформа використовує власний синтаксис макросів ({aff_sub}, #s1#, %SUBID% тощо) → вона шле literal або порожнє значення. Це найчастіша причина рівно такого симптому (200 + порожній subid): postback доходить, але макрос не розгортається.
  8. Приймання postback у Keitaro. Keitaro чекає параметр з іншою назвою (напр., постбек шле subid, а в налаштуваннях Keitaro клік-ідентифікатор мапиться на sub_id_1 або кастомний параметр) → значення приходить, але не матчиться з кліком.

2. Покроковий чекліст діагностики

КрокЩо перевіряюЩо має бути / що виправити
1. Тестовий клікПроходжу весь ланцюжок сам: клік по кампанійному лінку Keitaro → у звіті кліків Keitaro відкриваю свій клік і копіюю реальний subid.Клік є, subid згенерований (напр. k7f3a9d2). Якщо кліка немає — оголошення веде повз трекер: замінити фінальний URL у Meta на кампанійний лінк Keitaro.
2. Keitaro → лендингДивлюсь адресний рядок після редиректу на лендинг (DevTools → Network, перший документ).Має бути site.com/?clickid=k7f3a9d2&fbclid=IwAR... з реальними значеннями. Якщо {subid} літералом або порожньо — виправити макрос у tracking URL кампанії. Якщо параметри зникли — знайти редирект (http/www/slash), який їх зрізає, і зберегти query при редиректі.
3. ЛендингКонсоль/localStorage: чи зчитано clickid; href кнопки CTA (DevTools → Elements).Clickid збережений і підставлений у вихідний лінк. Якщо ні — виправити скрипт зчитування (назва параметра!) та генерацію лінка.
4. Лендинг → платформаКлікаю CTA, у Network дивлюсь весь ланцюжок редиректів до фінального URL казино; потім у кабінеті платформи — чи має мій тестовий клік/реєстрація sub-параметр.Subid присутній у фінальному URL у тому параметрі, який платформа документує як свій sub (напр. aff_sub=k7f3a9d2). Якщо губиться на хопі — лагодити той хоп; якщо параметр не той — перейменувати в лінку.
5. Якщо subid= порожній або ${subid} літералом — замінити макрос на синтаксис саме цієї платформи (з її документації), який повертає значення її sub-параметра.
6. Приймання в KeitaroЛог postback у Keitaro (Maintenance → Postbacks / клік → конверсії) + ручний тест: curl "https://tracker.com/postback?subid=k7f3a9d2&status=ftd&payout=10" з реальним subid з кроку 1.Ручний postback має прив'язати конверсію до кліка. Якщо прив'язує — Keitaro налаштований правильно і проблема вище (кроки 4–5). Якщо ні — звірити назву параметра клік-ідентифікатора та мапінг статусів (ftd → потрібний статус конверсії) у налаштуваннях кампанії/джерела.

Логіка порядку: крок 6 (ручний curl) можна виконати одразу після кроку 1 — це миттєво ділить ланцюжок навпіл: якщо ручний postback працює, проблема точно між лендингом і платформою (найімовірніше — макрос у шаблоні postback, п. 7 вище).

Ключовий принцип: на кожному переході значення живе в параметрі, який приймаюча сторона реально читає, а макрос у шаблоні — це завжди синтаксис відправляючої сторони: у tracking URL — макроси Keitaro ({subid}), у postback URL — макроси платформи ({aff_sub} тощо). Помилка «вписати ${subid} у кабінеті платформи» і дає симптом із умови: HTTP 200, subid порожній.
