# Завдання 2 — Діагностика втрати Click ID у зв'язці Meta → Keitaro → Landing → Platform → Postback

**Симптом:** кліки в Keitaro фіксуються, postback від платформи приходить з HTTP 200, але `subid` у ньому порожній → конверсії (FTD) не прив'язуються до кліків.

**Postback платформи:** `https://tracker.com/postback?subid=${subid}&status=ftd&payout=${amount}`
**Tracking URL на лендинг:** `https://site.com/?clickid={subid}&fbclid={fbclid}`

---

## 1. Усі можливі точки втрати Click ID

Ланцюжок: **Keitaro → (redirect) → Landing → (CTA-клік) → Casino/Affiliate platform → (конверсія) → Postback → Keitaro**. Subid може загубитись на КОЖНОМУ переході:

### Точка 1 — Keitaro: tracking URL / кампанія
- Макрос `{subid}` не підставляється: помилка в синтаксисі макроса (наприклад, `{sub_id}`, `{{subid}}`, `%7Bsubid%7D` — уже URL-енкоджений), або в потоці/кампанії використаний неправильний шаблон URL.
- Кампанія працює в режимі, де subid не генерується, або редирект іде повз трекер (пряме посилання на лендинг у рекламі замість посилання Keitaro).

### Точка 2 — Редирект(и) між Keitaro і лендингом
- Проміжні редиректи (клоака, HTTPS-редирект, www → без www, слеш у кінці) відкидають query string.
- Лендинг на іншому домені робить власний redirect (наприклад, `/` → `/index.html` чи мовний редирект), який не зберігає параметри.

### Точка 3 — Лендинг: зчитування і збереження
- Лендинг не читає `clickid` з query string взагалі.
- Читає, але не зберігає: користувач погуляв по сторінках/повернувся пізніше — параметр зник (немає localStorage/cookie).
- SPA-роутер «чистить» URL (history.replaceState) до того, як параметр зчитано.

### Точка 4 — Лендинг → платформа: передача при кліку на CTA
- **Найчастіша точка втрати.** Посилання на казино захардкоджене без параметрів: `https://casino.com/promo` замість `https://casino.com/promo?subid=abc123`.
- Параметр передається, але під неправильним ім'ям: платформа чекає `subid` (або `s1`, `aff_sub`, `cid` — залежить від платформи), а лендинг шле `clickid`.
- Значення не URL-енкоджене і ламається на спецсимволах.

### Точка 5 — Платформа: збереження subid
- Платформа отримала subid, але він не записався в її систему: не налаштований мапінг вхідного параметра на внутрішнє поле (aff_sub / s2s token).
- Реєстрація і депозит відбулись у іншій сесії/браузері/девайсі — платформа не зв'язала депозит із кліком, subid у конверсії порожній.

### Точка 6 — Платформа: шаблон postback
- У постбеку на боці платформи макрос прописаний невірно: `subid=${subid}` — але в системі платформи цей макрос називається інакше (`{aff_sub}`, `#s1#`, `{clickid}`), тому підставляється **порожній рядок** — і це в'яжеться з симптомом: запит доходить (200), а значення немає.
- Постбек шле статичний URL без макросів (хтось скопіював приклад з доків як є — `${subid}` буквально або порожньо).

### Точка 7 — Keitaro: прийом postback
- Keitaro чекає параметр з іншим ім'ям: у налаштуваннях постбека Keitaro click ID приймається як `subid`, але кампанія налаштована на інший параметр, або в S2S-постбеку вказано неправильне ім'я.
- Postback приходить на неправильний домен/кампанію (інший трекер-домен, тестова кампанія) — 200 віддається, але клік не знаходиться.

> HTTP 200 ≠ «все ок»: трекер відповідає 200 навіть коли не знайшов клік — тому статус-код тут нічого не гарантує.

## 2. Покроковий алгоритм діагностики

Принцип: іти по ланцюжку **зліва направо** і на кожному кроці дивитись, чи «живий» subid, — так проблема локалізується за один прохід.

**Крок 0. Зафіксувати тестовий клік.**
Зробити власний клік по tracking URL кампанії → у звіті кліків Keitaro знайти його subid (наприклад, `k7f3a92b1c4d5`). Далі скрізь шукаємо саме це значення.

**Крок 1. Keitaro: tracking URL.**
Перевіряємо: у налаштуваннях кампанії/потоку URL лендинга містить саме `{subid}` (валідний макрос Keitaro), і в тестовому переході браузер реально приходить на лендинг з `?clickid=k7f3a92b1c4d5` (DevTools → Network → перший запит на site.com, дивимось фінальний URL після всіх редиректів).
*Якщо параметра немає/порожній:* виправити макрос у tracking URL; прибрати проміжні редиректи або переконатись, що вони зберігають query string.

**Крок 2. Лендинг: зчитування.**
Відкриваємо лендинг з тестовим `?clickid=...` → консоль/localStorage: чи зчитано і збережено значення; чи є воно в прихованих полях форми / dataLayer.
*Якщо ні:* додати зчитування з query string при завантаженні і збереження в localStorage/cookie (first-touch), щоб параметр переживав навігацію.

**Крок 3. Лендинг → платформа: CTA-лінк.**
Наводимо на кнопку/дивимось href у DevTools і сам редирект у Network: чи містить посилання на платформу `subid=k7f3a92b1c4d5` **під тим ім'ям параметра, яке документує платформа**.
*Якщо ні:* дописати динамічну підстановку збереженого значення в CTA-посилання, звірити ім'я параметра з документацією платформи (subid / s1 / aff_sub / cid).

**Крок 4. Платформа: чи бачить вона subid.**
У кабінеті партнерки відкриваємо звіт по кліках/конверсіях: чи відображається наш subid у тестовому кліку.
*Якщо ні:* проблема в кроці 3 (ім'я параметра) або в налаштуваннях офера на платформі — звертаємось у підтримку/налаштовуємо мапінг вхідного параметра.

**Крок 5. Платформа: шаблон postback.**
Дивимось налаштування постбека в кабінеті платформи: URL має містити **макрос платформи** (у кожної свій синтаксис!), напр. `...postback?subid={aff_sub}&status=ftd&payout={amount}`. Робимо тестову конверсію (або просимо test postback у підтримки) і перевіряємо в логах, який URL реально відправився.
*Якщо в реальному запиті `subid=` порожній:* замінити макрос на правильний для цієї платформи — це і є найімовірніша причина нашого симптому (200 + порожній subid).

**Крок 6. Keitaro: прийом postback.**
Keitaro → Maintenance → Logs → Postbacks (журнал вхідних постбеків): чи приходить запит, з яким subid, і чи знайдено клік. Вручну дьорнути `https://tracker.com/postback?subid=k7f3a92b1c4d5&status=ftd&payout=50` — конверсія має з'явитись у кампанії.
*Якщо вручну працює, а від платформи ні* — остаточний доказ, що винен шаблон постбека платформи (крок 5). *Якщо і вручну не працює* — перевірити ім'я параметра click ID у налаштуваннях постбека Keitaro та мапінг статусу `ftd` на ціль конверсії.

## 3. Що саме змінюється на кожному етапі, якщо проблема там

| Етап | Що перевіряємо | Що виправляємо |
| --- | --- | --- |
| Keitaro tracking URL | наявність `{subid}` у URL лендинга, фінальний URL у браузері | синтаксис макроса; редиректи, що ріжуть query |
| Лендинг (вхід) | параметр зчитано і збережено (console/localStorage/приховані поля) | додати capture з query string + persist |
| Лендинг → платформа | href CTA містить subid під правильним ім'ям | динамічна підстановка; ім'я параметра з доків платформи |
| Платформа (вхід) | subid видно у звіті кліків партнерки | мапінг вхідного параметра на aff_sub |
| Платформа (postback) | реальний відправлений URL у логах постбеків | правильний макрос платформи замість порожнього/чужого |
| Keitaro (прийом) | журнал постбеків: запит прийшов, клік знайдено, ціль засчитано | ім'я параметра subid у постбеку; мапінг статусу ftd |

## 4. Приклад коректного ланцюжка з реальними значеннями

Нехай Keitaro згенерував клік із `subid = k7f3a92b1c4d5`, а fbclid від Meta — `IwAR2xYz123`.

**1) Tracking URL (налаштований у кампанії Keitaro, стоїть у рекламі Meta):**
```
https://site.com/?clickid={subid}&fbclid={fbclid}
```
→ після підстановки макросів Keitaro користувач приходить на:
```
https://site.com/?clickid=k7f3a92b1c4d5&fbclid=IwAR2xYz123
```

**2) Лендинг** зчитує параметри з query string, зберігає в localStorage і підставляє в CTA-посилання «Play now»:
```
https://casino.com/promo?subid=k7f3a92b1c4d5&fbclid=IwAR2xYz123
```
(ім'я `subid` — саме те, яке документує платформа; значення — те саме, без змін)

**3) Платформа** записує клік: `aff_sub = k7f3a92b1c4d5`. Користувач реєструється і робить депозит $50 → платформа формує postback за своїм шаблоном:
```
https://tracker.com/postback?subid={aff_sub}&status=ftd&payout={amount}
```
→ реально відправляється:
```
https://tracker.com/postback?subid=k7f3a92b1c4d5&status=ftd&payout=50
```

**4) Keitaro** приймає постбек, знаходить клік `k7f3a92b1c4d5`, засчитує конверсію зі статусом `ftd` і payout $50 → у статистиці кампанії конверсія прив'язана до конкретного кліка, креативу й адсету Meta.

Ключове правило ланцюжка: **значення subid ніколи не трансформується** — міняються лише імена параметрів на стиках (clickid → subid → aff_sub → subid), і кожне ім'я має відповідати тому, що чекає приймаюча сторона.
